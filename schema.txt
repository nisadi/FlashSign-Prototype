FLASHSIGN DATABASE SCHEMA
=========================

Format:   table - column - type - key / allowed values / note
          pk = primary key, fk = foreign key (-> the table it points to)
          Lines starting with * are extra rules (unique combinations, checks, notes).
          Text after a type lists the allowed values or explains the column.

General rules:
  - Every table has its own uuid primary key named <table>_id.
  - Lists are their own tables (e.g. task_tag, meeting_participant), never comma-separated text.
  - Nothing is stored twice and nothing is stored that can be counted or calculated
    (member counts, project progress, task count per phase, seal usage count, phase and contract
    "expiring / missed" states, file size and page count come from stored_file).
    The few deliberate exceptions are marked "kept on purpose" with the reason.
  - Allowed values are checked by the app (varchar + check list), not database enums,
    so a new value needs no schema change.
  - Files are not stored in the database: they live in object storage and stored_file holds
    their details. Other tables point to stored_file. No Base64 / data URLs in any column.
  - Passwords, tokens and codes are stored only as hashes.
  - Emails are stored lower-case. Times are stored in UTC (timestamp); a date with no time
    (start_date, due_date) is a calendar day in the organisation's time zone.
  - created_at / updated_at on tables whose rows are edited; deleted_at where something can go to
    the Trash (soft delete).

How an organisation comes to exist (the onboarding flow):
  1. A Super Admin (platform_admin) works in the Super Admin Dashboard. They either
     - create an organisation directly (organization with name, slug, plan, industry, size and a
       starting status), which also sends an organization_invitation to the Owner's email, or
     - invite an organisation (organization_invitation with organisation name, Owner email, plan
       and a note, valid 7 days); the organization row is created when the Owner accepts.
     The Super Admin can resend or revoke invitations and edit, deactivate or delete organisations.
  2. The Owner opens the invitation link, signs up or signs in (users, verification_code), and
     becomes organization.owner_user_id. The organisation's status becomes active.
  3. The system copies the platform's default roles (role_template) into the organisation's own
     role rows (Organization Owner, Project Manager, Team Lead, Developer, QA Tester) and makes the
     Owner the first org_member with the Organization Owner role.
  4. The Owner (or a Team Management role) edits these roles and creates custom ones (role).
  5. The Owner (or a Team Management role) invites members (invitation with a role_id and, for
     Project User Access roles, the assigned projects in invitation_project). Accepting creates or
     links the account, an org_member with that role, and project_member rows for the projects.

Access model (what a person can open and do):
  - Super Admin = has a platform_admin row. Sees only the Super Admin Dashboard, never an
    organisation's workspace.
  - Organization Owner = organization.owner_user_id. Always has full access, whatever the settings
    of their role. Only the Owner can open Settings > Preferences and AI Agent Hub > Organisation.
  - Everyone else: one role per member (org_member.role_id). A role has four settings:
      admin_dashboard / my_status   which dashboards; the default is the Admin Dashboard if allowed,
                                    otherwise My Status; with both, a switcher is shown
      project_access                management = every project, create / edit / delete, Reports,
                                    Settings and Danger Zone; user = only projects where the person
                                    has a project_member row, Settings view-only, no Reports or
                                    Danger Zone, no project creation
      my_tasks_access               My Tasks shown and allowed or not
      team_access                   management = Team Analytics, invite / edit / remove members,
                                    Roles & Permissions; member = view members only
  - Planner and Agreements are open to every organisation member (no setting).
  - Every page, API call and action checks these; hiding a menu item is never the only check.

Multi-tenancy - shared database, shared schema:
  - All organisations (tenants) live in one database, one schema and the same tables.
    Rows are kept apart by organization_id.
  - Every tenant table has organization_id (not null, fk -> organization), right after its
    primary key - child tables too (task_tag, signer, board_column ...), even though they could
    reach it through their parent. This is a deliberate exception to "nothing stored twice":
    every query, index and security policy can filter by tenant without joins.
  - Global tables have no organization_id and are marked "* global table": the platform tables
    (platform_admin, organization_invitation, role_template, notification_event,
    platform_activity_log) and the person's own tables (users, session,
    verification_code, user_preference, user_notification_setting, saved_signature).
  - No cross-tenant links: every tenant table also has unique (organization_id, <table>_id), and
    every foreign key from one tenant table to another includes organization_id, e.g.
      task (organization_id, project_id) -> project (organization_id, project_id)
    Foreign keys to global tables (users, role_template ...) stay plain; the app checks that a
    referenced person is an active org_member of that organisation.
  - Row-level security (PostgreSQL RLS) on every tenant table:
      organization_id = current_setting('app.organization_id')::uuid
    The API runs SET LOCAL app.organization_id at the start of each transaction, taken from
    session.active_organization_id (or from the agent_access_token / signing_token used).
    The app's database role does not own the tables and cannot bypass RLS.
  - Super Admins work through the global tables and organisation records (name, slug, plan,
    industry, size, status, Owner). They get no automatic access to a tenant's content: that needs a
    support_access_grant approved by the organisation, and every use is logged.
  - Background jobs (reminders, expiry, idle time-outs, email sending) use a separate database
    role that bypasses RLS; everything they change is written to activity_log.
  - Public signing links: a signer without an account is resolved from signing_token by one
    narrow security-definer function that returns only the token's organization_id; the rest of
    the request then runs under that organisation like any other.
  - Unique rules on anything other than uuids are per organisation, e.g.
    unique (organization_id, project_key). Only organization.slug, users.email,
    stored_file.storage_key, role_template.role_key and the token_hash columns are unique across
    all organisations.
  - Every index on a tenant table starts with organization_id.
  - Object storage keys start with the tenant: org/<organization_id>/... ; personal files
    (avatars, saved signatures) use user/<user_id>/... and have an empty stored_file.organization_id.
  - Removing an organisation: soft delete (organization.deleted_at), then after the retention
    period delete every row with its organization_id and its org/<id>/ prefix in object storage,
    except signed agreements under retention or legal hold.

Feature flags: teams and contracts are hidden in the app today (organization_feature) but their
tables are included.

                          created_at                 - timestamp
                          updated_at                 - timestamp
